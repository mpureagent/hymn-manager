## 三、验收中发现的数据缺陷（我方责任，已修）

这是本轮最有价值的发现。Qoder 报告"找到 3–60 首"时被当成正常，但 PM 逐条看内容发现是**噪音**：

| 现象 | 根因 | 影响 |
|---|---|---|
| 输入 `1`，红本 5 条、千首本 60 条 | 歌词行残留段号 `1 全能上帝`、`169下_举起双手`、`404慈悲救主` | 编号检索被淹没 |
| 首句显示 `[00:09.84]我要举起我手` | **行首有空格/BOM 时 `^` 锚点失配**，时间轴没剥掉 | 歌词与检索都被污染 |
| 首句显示 `词：诗34：1-14`、`歌手：常用诗歌本` | 元信息行未过滤 | 投屏会显示这些垃圾 |

修复（`ad29127`）：

1. `clean_lines` 先 `strip()` 并去 BOM，再循环剥时间轴（一行可有多个）。
2. 段号前缀仅当等于本首编号时剥；`split_verses` 支持 `1` / `1.` / `1：` / `169下` 等标记（祷文编号转为 verse label，内容不丢）。
3. 过滤元信息行与经文引用行。
4. 新增 **`tools/check_data_quality.py`** 硬断言：时间轴/BOM 残留、段号残留、杂行、元信息残留**必须为 0**，并校验两本第1首歌词不同。不达标非零退出。

修复后实测：

```
black_book_1218: 1217 条，有歌词 1193，时间轴 0，段号 0，杂行 0，元信息 0
red_book:        442 条，有歌词 400，时间轴 0，段号 0，杂行 0，元信息 0
跨本校验：红本①与千首本①为不同译文 ✓
```

编号检索噪音：红本 **5 → 1**，千首本 **60 → 1**。

## 四、P2 建议（不阻塞）

1. 纯数字查询建议只匹配编号与含该数字的标题，不匹配首句正文——即使将来数据再有脏行，编号检索也不会被污染。属防御性设计，可并入后续单。
2. 结果列表行高偏大（约 60px），1200 条浏览时可考虑紧凑模式。
