## 三、验收中发现的数据缺陷（严重，已修 `adae1d0`）

### 现象

红本第1首《圣哉三一歌》在数据里是 **1 段**，UI 也不显示段号。但实体书明明是 4 段（1./2./3./4.）。核对源 LRC：

```
[00:19.07]1.圣哉，圣哉，圣哉！全权的神明
[01:03.62]2.圣哉，圣哉，圣哉！众圣都崇敬
```

段号就在行首，**是我上一轮的清洗规则吃掉了**：

- `JUNK` 里有 `^第?\s*\d{1,4}\s*[_．.、\-]` —— 本意是清 `254_教会根基` 这类编号前缀，结果把 `1.圣哉…` 整行当垃圾删了
- 我先加的 `SELF_NUM` 剥离也会把「1.」当诗歌编号吃掉

### 后果

- 红本 400 首里只有 **3 首**保留分段（正确值应是绝大多数）
- 千首本 **0 首**有分段
- **投屏（T5）无法按段分页**，长歌只能按行硬切——这是会直接影响聚会现场的问题

### 修复

1. `JUNK` 移除会误吃段号的编号-分隔符规则
2. `SELF_NUM` 增加 `_is_verse_marker()` 护栏：行首 1–20 的小数字 + 分隔符/空格 → 视为分段标记，不当编号前缀剥
3. **1218 的新发现**：源站 LRC 没有段号，但用**空行分段**（1272 首里 987 首有 ≥3 空行）。`clean_lines` 保留 `None` 作为段落分隔信号，`split_verses` 据此切段
4. `check_data_quality.py` 增加段落结构断言：多段条目占比 < 50% 即判失败，防止再次静默退化

### 修复后实测

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 红本 多段条目 | 3 / 400 | **285 / 400** |
| 千首本 多段条目 | 0 / 1193 | **1087 / 1193** |
| 红本第1首 | 1 段 | **4 段（段号 1/2/3/4）** |
| 千首本第1首 | 1 段 | **4 段** |

段数中位数两本都是 3，最多红本 12 段、千首本 24 段。

## 四、P2 建议

1. 搜索历史会记录用户为了定位而输入的编号（如我测试时输入的 `389`）。这符合"明确打开即记录"的规格，但若你希望历史里只留歌名类搜索，可在 T4 加开关。
2. 相对时间「刚刚 / 1 分钟前」需要每分钟刷新，Qoder 已实现，建议 T5 后抽查长时间挂机是否漂移。
