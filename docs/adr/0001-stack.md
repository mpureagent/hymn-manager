# ADR-0001 技术栈：Electron 22 + Vite + TS + vanilla DOM

状态：已定
日期：2026-10-22

## 背景

需要一个 Windows 桌面应用，能开两个窗口（主控 + 全屏投屏）、离线、可打包成安装器。上一项目 bible-projector 已用 Electron 22.3.27 + Vite 5 + TS 5 跑通 M1–M4（198 测试全绿、NSIS/portable 出包成功、wine 交叉打包验证过）。

## 决策

沿用同一基线：

- Electron 22.3.27（固定版本，不用 latest）
- TypeScript 5.6 + Vite 5.4 + vitest 2
- 渲染层写**原生 DOM 模块**，不引入 React/Vue
- 状态集中在一个 store 对象 + 显式 render 函数

## 理由

1. **双窗口与 IPC 已在该基线上验证过**，包括投屏窗口的创建/跟随/关闭时序，照搬可省掉一类只有真机才会暴露的问题。
2. **零 UI 框架依赖**：这个应用是"一个列表 + 一个预览 + 一组设置项"，DOM 足够；省掉的构建复杂度直接换来打包体积和启动速度，也少一类"框架版本与 Electron 22 不兼容"的风险。
3. **可测性**：核心逻辑（检索排序、归一化、历史去重、样式解析）放纯函数，vitest 直接测，不依赖 DOM。
4. bible-projector 的经验可以直接复用：CSP 注入脚本、字体枚举、样式应用方式。

## 后果

- 正面：依赖少、打包小、与已有实践一致、能复用脚本。
- 负面：复杂交互（虚拟列表、拖拽）要手写。本应用列表是固定行高的平铺列表，虚拟滚动实现量可控。
- 未来若要换成 React，只需替换 view 层，store 与 shared 纯函数不动。

## 备选与否决理由

| 备选 | 否决理由 |
|---|---|
| Tauri | Windows WebView2 版本差异导致字体渲染不一致，投屏场景不能接受 |
| Electron latest | 版本漂移风险，bible-projector 已验证 22 稳定可用 |
| React + MUI | 为三个面板引入整套框架，收益不抵体积与构建复杂度 |
